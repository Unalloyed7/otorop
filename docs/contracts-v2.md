# Контракт проверяемых утверждений v2

Дата: 12.11.2026. Источник формата — schemas.py, примеры — examples/. Формат опубликован в репозитории для №1 и №3; отдельного подтверждения приёмки другими участниками пока нет. По поручению пользователя реализованы и движок №2, и рабочее место №3.

Старые поля Evidence, SearchFilters и Answer сохранены. Новые поля имеют значения по умолчанию. Клиентам с прежними строгими Pydantic-моделями нужно обновить schemas.py: extra=forbid намеренно сохранён. Веб и конкурсный CSV вызывают один LegalAssistant.

## Answer и утверждения

Answer сохраняет status/text/citations/missing_info и добавляет schema_version=2, statements, scenario, verification.

В statements хранится каждое прошедшее разбор утверждение, включая отклонённое. published=true означает, что вывод включён в итоговый ответ. Противоречивое или недостаточно подтверждённое утверждение не публикуется как юридический вывод; его текст остаётся в карточке для исследования с соответствующей отметкой.

| Поле VerifiedStatement | Смысл |
|---|---|
| statement_id | Идентификатор записи, полученный из структурированного черновика; не юридический идентификатор нормы. |
| text | Проверяемое утверждение. |
| subject | contract_number, counterparty, employee; неизвестное остаётся null. |
| rule | duty / permission / restriction / information. |
| value | description, amount, currency, duration, unit, day_type, counted_from, action. Например: 30, дней, calendar, подписание УПД. |
| conditions | Текст, ключ/ожидаемое значение, результат met/not_met/unknown и точные цитаты. |
| period | Установленные valid_from, valid_to и date_kind; неизвестная граница null. Это период нормы, не дата пользователя. |
| supports | Точные Citation, подтверждающие данный вывод. |
| limitations | Ограничения, исключения, изменения, другая редакция, противоречие или дополняющий порядок. |
| relations | Связи положений №1: исходный и целевой фрагменты, точные подтверждения связи, confidence и статус типа. |
| check | status, mechanical_pass, semantic_checked, reasons. |
| published | Включён ли вывод в Answer.text. |

| check.status | Отображение | Смысл |
|---|---|---|
| confirmed | Подтверждено | Формальные проверки пройдены, модель подтвердила смысловую связь по переданным основаниям. |
| conditional | Подтверждено при условиях | Правило подтверждено условно; неизвестные обстоятельства не объявлены выполненными. |
| contradiction | Найдено противоречие | Вывод не включается в итоговый ответ; рядом сохраняются противоречащие положения. |
| insufficient | Недостаточно оснований | Формальная или смысловая проверка не пройдена либо не выполнена. |

Числа, известные субъекты, даты и ссылки проверяются кодом. Смысл, сфера действия, исключения и связь нескольких норм проверяются отдельным вызовом модели. semantic_checked=true означает выполненную проверку, а не гарантию истинности. Не делайте из него процент уверенности.

Citation по-прежнему получает настоящие document_id/chunk_id, название, пункт и точный диапазон исходного текста из Evidence. Добавлены role и applicability. role: support/restriction/contradiction/amendment/exception/other_edition/procedure/relation. Короткие e1/d1 существуют только внутри HTTP-запроса модели и наружу не возвращаются.

## Четыре даты и точность

SearchFilters.scenario и Answer.scenario используют ScenarioDates:

```json
{
  "contract_signed": "август 2024",
  "specification_signed": "2024-10-02",
  "delivery": "2024-10-18",
  "event": "2024-11",
  "facts": {"standard_form_unchanged": true, "foreign_counterparty": false}
}
```

Строки нормализуются в DateSpan: start включается, end_exclusive исключается, precision=day/month/year/range, label сохраняет исходную запись. Август 2024 — [2024-08-01, 2024-09-01), а не событие 1 августа. Поддержаны ISO-дни, месяцы, годы, русские даты и диапазон через `..`; последняя дата/месяц/год диапазона включается целиком.

governing_date выбирает обстоятельство для редакции нормы. Дата спецификации проверяется отдельно для соответствующего условия допсоглашения. Если внутри диапазона меняется условие или правило, движок просит уточнение. Буквально одинаковые положения двух редакций могут совместно покрыть весь интервал; тогда нужны цитаты обеих редакций. Смысловое равенство перефразированных норм код автоматически не предполагает.

event_date/date_kind остаются для прежних клиентов и явного as_of. Противоречивые даты одного обстоятельства запрещены. Непустые даты формы уточняют извлечённые из истории; пустая форма не стирает известный месяц. as_of задаёт точный день выбранного события. Переданные scenario.facts — данные пользователя; неизвестное значение не равно false.

## №1: основания и ограничения

Метод search(query, filters) и SearchResult сохранены. filters.purpose=grounds — основной поиск; limitations — отдельный поиск ограничений. anchor_document_ids связывает его с уже найденными документами. Текущий адаптер включает связанные допсоглашения, исключения и общие регламенты, а также другие редакции. Число выдач и размер контекста ограничены.

Неприменимая редакция остаётся в контексте с metadata.temporal_status=not_applicable: использовать её как действующее подтверждение нельзя, но можно показать в limitations и сравнении. Историческую редакцию закона нельзя достраивать по памяти.

Существующий формат условий №1 сохранён:

```json
{"kind":"specification_signed_at","operator":"after","date":"2024-10-01","source_text":"...точное условие..."}
```

Для диапазона спецификаций код возвращает applicable/not_applicable/unknown/varies. after исключает саму опорную дату. Просьба к №1: расширять структурированные предикаты только вместе с их точным source_text и координатами; дату подписания документа не подменять датой спецификации. Неизвестное фактическое обстоятельство сохранять неизвестным. Одного resolved=true недостаточно для доказательства применимости.

## Бюджет и восстановление

По умолчанию: MAX_MODEL_CALLS=6, MAX_SEARCH_CALLS=3, QUESTION_TIMEOUT=240. Текущий цикл выполняет основной поиск и один дополнительный при SEARCH_RETRIES=1. Эти пределы общие для ответа, а не для каждого этапа отдельно. При использовании пакетов №1 учитывается каждый прямой поисковый запрос; один слот резервируется для ограничений. Внутренний рекурсивный recovery пакета в движке выключен: повтором управляет общий бюджет. Непроверенные отдельным запросом части перечисляются в verification.query_parts_omitted; их наличие само по себе не доказывает отсутствие основания, поскольку общий контекст запроса сохраняется.

Одна попытка исправления делится между неверным JSON, возвращённой схемой, неизвестным полем, некорректными индексами проверяющего и несуществующей/неточной ссылкой. Модель получает конкретные ошибки и допустимую структуру в недоверенных данных. Повторное исправление запрещено. Обычная сетевая/HTTP-ошибка не считается ошибкой JSON и этим механизмом не исправляется; HTTP-повторы API_RETRIES остаются отдельными и конечными.

Уже проверенные части при сбое дополнительной проверки сохраняются в partial с явным пробелом. Технический сбой не становится утверждением об отсутствии нормы. Числа/даты/ссылки проверяются и после исправления. verification сообщает использованный бюджет и факт поиска ограничений; этот флаг не означает исчерпывающий просмотр всей базы.

VERIFY_ANSWER=0 — экспериментальный режим: ответ становится partial с предупреждением, statements не помечаются опубликованными и прошедшими смысловую проверку. Рабочий режим — VERIFY_ANSWER=1.

## №3: подключение

```python
result = await engine.answer(
    messages,
    scenario={"contract_signed": "август 2024", "specification_signed": "2024-10-02"},
    on_progress=lambda event: save_progress_for_this_job(event),
)
```

Промежуточные события содержат этапы и найденные источники; итоговый текст публикуется только после завершения проверки. Карточка показывает supports и limitations именно выбранного statement_id. Неподтверждённый текст не следует оформлять как готовую рекомендацию. Для исследования данных используются examples/statement-statuses.json и examples/answer.json; они никогда не передаются в рабочий поиск или генерацию.

Сквозная регрессия «общее правило → исключение → допсоглашение → условный вывод» закреплена в tests/test_verification_v2.py. Браузерная проверка показывает сравнение, изменение обстоятельств, повторную проверку, устойчивые задания и локальные оценки.


## Совмещение с конвейером №1

Включены изменения основной ветки до ee6c666: структурные положения, search_bundle/bundle_result, граф связей, покрытие и возобновляемые кэши. Комплект зависимостей помещается в контекст целиком либо возвращается явный пробел; условия не отрезаются незаметно ради top_k. Сведения о пакетах и пропусках сохраняются в диагностике.

VerifiedStatement.relations содержит связи, относящиеся к выбранному утверждению, только если исходный и целевой chunk_id присутствуют и точная quote находится в переданном подтверждающем фрагменте. UI показывает их как связи источников, а type_status=candidate — как кандидатов. confidence=explicit или точная цитата не доказывают юридическую истинность типа связи; inferred и possible_exception_to не становятся установленными исключениями. Окончательный вывод отдельно проходит проверку модели.

KNOWLEDGE_LLM_EXTRACTION и KNOWLEDGE_RELATION_REVIEW по умолчанию выключены. При явном включении их генеративные вызовы внутри ответа также используют общий модельный бюджет; для массового извлечения лучше отдельно подготовить и проверить кэш конвейера №1.
