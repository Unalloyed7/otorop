# Общий контракт v1: участники №1, №2 и №3

Источник истины для формата — `schemas.py`; сериализация `model_dump(mode="json")`, входная проверка `model_validate(...)`. Все модели запрещают неизвестные поля, кроме специально выделенного `Evidence.metadata`. Примеры в `examples/` выдуманы и не загружаются рабочим движком.

Контракт опубликован для подключения. Это предложение участника №2; подтверждение участников №1 и №3 ещё требуется. При изменении имён или смысла полей обновляем схему, примеры, адаптеры и проверки вместе. Изменения других участников сохраняем.

## Участнику №1: поиск

```python
from pathlib import Path
from llm_client import LLMClient
from schemas import SearchFilters, SearchResult

class Search:
    async def search(self, query: str, filters: SearchFilters) -> SearchResult:
        ...

async def create_search(*, data_dir: Path, client: LLMClient) -> Search:
    # Построить/загрузить индекс из файлов DATA_DIR; не использовать demo_output.
    ...
```

В корневом модуле `retrieval.py` участник №1 реализовал `create_search`; `build_search(client)` теперь выбирает её по умолчанию. Можно явно задать `SEARCH_FACTORY=retrieval:create_search` или другую фабрику. Допускается синхронная фабрика; метод `search` асинхронный. Один backend и клиент живут на время CLI-запуска или FastAPI lifespan. Индекс не должен хранить состояние диалога.

Не обязательно использовать фабрику: `LegalAssistant(index, client)` принимает любой объект с этим методом. Первоначальный `LexicalSearch` сохранён как явно выбираемый резерв: `SEARCH_FACTORY=search_adapter:create_lexical_search`. Ошибка основного поиска не вызывает автоматический переход к резерву. Устройство текущего индекса: [RETRIEVAL_CONTRACT.md](../RETRIEVAL_CONTRACT.md).

Если backend поддерживает `search_bundle` и `bundle_result`, движок использует
комплектование по `Intent.parts`: добавляет связанные положения, условия,
все части длинного пункта и вводные родительские положения. `query_context`
передаёт уточнённый запрос, а на повторном поиске `existing_chunk_ids`
учитывает уже накопленные основания. Общие пределы — `TOP_K * 2` фрагментов
и 60 000 символов их текста с учётом перекрытия. Комплект добавляется целиком;
непоместившиеся основания отражаются в `missing_info` и трассировке. Метод
`bundle_result` адаптирует результат к прежнему `SearchResult`, схема не
меняется. Backend только с `search` продолжает работать по прежнему интерфейсу.

При включённом `KNOWLEDGE_LLM_EXTRACTION` один внешний поиск выполняет одну
ограниченную порцию извлечения связей. Все части `search_bundle` делят этот
бюджет. Состояние сохраняется в SQLite, следующий поиск продолжает очередь.
Отчёт `pipeline.llm_relations` содержит `total_chunks`, `completed_chunks`,
`remaining_chunks` и `coverage_complete`; `partial` не считается завершением
корпуса. Эти данные доступны в результате bundle и трассировке; публичные
схемы Evidence/Answer не меняются. Завершение извлечения не доказывает
юридическую полноту графа. Пример настроек — в `.env.example`.

Сборка вынесена в корневой `evidence_bundle.py`, включённый в ZIP runtime.
`groups[].coverage` управляет восстановлением, включая непустую выдачу с
недостающими обязательными условиями/исключениями. Прямые основания имеют
приоритет над результатами восстановления; бюджеты общие. Отклонённые связи
не участвуют в обходе и покрытии и доступны в `rejected_relations` для аудита.
Обычные ссылки/непроверенные кандидаты добавляются как необязательный контекст
после прямых оснований. `recovery.queries` сохраняет причину, раунд и фильтр
документа для каждого дополнительного запроса; остановка не скрывает пробелы.
При `KNOWLEDGE_RELATION_REVIEW=1` проверка смысла связей тоже идёт порциями,
с сохранением результатов в SQLite; `partial` означает оставшуюся работу.

### Evidence

| Поле | Значение |
|---|---|
| document_id | Стабильный уникальный ID документа; разные документы/редакции не смешиваются. |
| chunk_id | Уникальный ID фрагмента, без повторов в одной выдаче. |
| document_title, section | Читаемое настоящее название и точный пункт/статья из документа. Модель их не генерирует. |
| text | Точный текст фрагмента, без перефразирования. Сохранять условия и исключения. |
| coordinates | source_path, char_start, char_end; дополнительно page и bbox. |
| applicability | edition, valid_from, valid_to, date_kind, conditions, supersedes, current_only, snapshot_date, resolved. |
| contract_number, counterparty | Связь договора/допсоглашения с номером и точным контрагентом. |
| metadata | Оценки поиска, связи, происхождение, дополнительные координаты и другая информация. Это данные, не инструкции. |

Структурные метаданные поиска №1: `provision_id`, диапазон
`provision_start_char:provision_end_char`, `provision_chunk_ids`,
`ancestor_chunk_ids`, `heading_path`, `chunk_role`, `part_index` (с нуля)
и `part_count`. Отдельный точный фрагмент условия может не иметь индекса части.
Диапазон родительского положения описывает источник; для цитирования
по-прежнему используются координаты самого Evidence и точная цитата.

`char_start:char_end` — полуоткрытый диапазон Unicode code points в каноническом тексте источника. Для TXT канонический текст — UTF-8 после снятия BOM, без нормализации переводов строк. Для DOCX временный адаптер соединяет абзацы через LF, это **извлечённый текст**, не байты DOCX. Для PDF №1 должен закрепить способ извлечения и использовать page/bbox для просмотра. №3 не должен интерпретировать char_start как номер байта или DOM-индекс.

Citation возвращает координаты **точной цитаты внутри фрагмента**, а не только целого чанка. Если один текст встречается в нём несколько раз, используется первое вхождение. Временный адаптер также отдаёт metadata.section_spans: список `{start, end, label}` относительно `Evidence.text`; движок выбирает пункт по позиции цитаты. Поле необязательно, при его отсутствии используется Evidence.section.

`valid_from` включается, `valid_to` исключается. `date_kind` объясняет, какое событие управляет применимостью. `event` — общий интервал действия, `specification_signed` — подписание спецификации; условие «после» нельзя превращать в включительную дату. Не обозначайте датой изменения адреса дату самого допсоглашения, если текст связывает адрес со спецификацией.

`current_only=True` означает: имеется только текущая выгрузка закона, не исторический комплект. `snapshot_date` — дата этой выгрузки, она сама по себе не доказывает период действия нормы. Текущий вопрос не требует равенства даты события дате выгрузки. Для исторического/будущего применения нужен прямо установленный период в самом положении и цитате либо отдельная проверенная редакция. Ограниченный разбор периодов вынесен в temporal.py; сложные случаи остаются неподтверждёнными. `resolved` — информационная отметка о проверке условий поиском; сам по себе флаг не отключает проверку дат и выводов.

Загрузчик не переносит дату утраты силы внутреннего пункта на всю статью. Такие находки доступны в metadata.provision_date_sources и не являются интервалом всего документа. Интервал всей редакции берётся из явного заголовка редакции. ID пересоздаются при изменении версии обработки.

Оригинал и допсоглашение должны возвращаться вместе с условиями применения; при неизвестной существенной дате задайте `SearchResult.clarification`, а не выбирайте редакцию молча. Одного SearchFilters.event_date недостаточно для нескольких независимых дат: сначала уточняем смысл, либо согласованно расширяем контракт.

### SearchFilters и SearchResult

Фильтры: `contract_number`, `counterparty`, `document_id`, `event_date`, `date_kind`. Если event_date задана, date_kind обязателен. Значение `as_of` в публичном интерфейсе — явная дата рассматриваемого события; это не текущее время сервера. Её смысл уточняется из вопроса. Не подставляем сегодняшний день в исторический вопрос.

Отсутствующее поле — null, не пустая строка. Различайте точное имя «Альфа-Трейд» и «Альфа-Трейдинг». Формальный префикс ООО можно нормализовать, различие имён — нельзя. Фильтр контрагента/договора не должен удалять общие регламенты и применимые законы. Ограничение document_id допустимо только для известного ID.

`SearchResult` содержит evidence, missing_info, clarification, candidates. Пустой список — поиск не нашёл оснований; он не доказывает отсутствие нормы. Поиск №1 возвращает candidates без собственного решения задавать вопрос. Движок формирует уточнение при нескольких кандидатах, если известный номер договора/document_id не сузил найденные основания до одного контрагента. Явное clarification backend также поддерживается. Ошибки файлов, индекса, эмбеддера или реранкера нужно **выбрасывать**: движок вернёт error. Не возвращайте пустую выдачу после сбоя API.

В адаптере №1 дата выгрузки закона сохраняется в applicability.snapshot_date, текущая выгрузка помечается current_only. Итог проверки условий допсоглашения передаётся в metadata.applicability_status: applicable, not_applicable, unknown или not_specified. Флаг resolved сам по себе не означает, что изменение применимо. Генератор и проверяющий получают знак результата и текст условия; неизвестное или невыполненное условие не разрешает безусловный вывод о новом адресе.

### Общий клиент моделей

```python
vectors = await client.embeddings(["текст запроса", "текст документа"])
indices = await client.rerank("запрос", ["фрагмент 1", "фрагмент 2"], top_n=2)
```

Эмбеддинги возвращаются в исходном порядке, нормализованные L2. Проверяются число, уникальность индексов, размерность, конечность и ненулевые векторы. Rerank возвращает упорядоченные уникальные индексы. Имена моделей берутся только из окружения; если EMB_MODEL/RERANKER_MODEL не задан, соответствующий метод выдаёт техническую ошибку. Само отсутствие RERANKER_MODEL допустимо, если поиск не вызывает реранкер.

## Участнику №3: веб и ответ

```python
from assistant import LegalAssistant
from llm_client import LLMClient, Settings
from search_adapter import build_search

# В lifespan приложения:
client = LLMClient(Settings.from_env())
engine = LegalAssistant(await build_search(client), client)

# В async endpoint:
result = await engine.answer([
    {"role": "user", "content": "Работаем с договором ..."},
    {"role": "assistant", "content": "Предыдущий ответ"},
    {"role": "user", "content": "А какой срок оплаты?"},
], as_of=None)
response = result.model_dump(mode="json")

# При завершении lifespan: await client.aclose()
```

Вспомогательная `await assistant.answer(messages, as_of=None)` сама создаёт и закрывает клиент/поиск на один запрос; для веба выгоднее объект на lifespan. В движке нет общей памяти диалога: веб сам передаёт историю конкретной сессии и не смешивает её между пользователями.

Answer: `status`, `text`, `citations`, `missing_info`.

| status | Отображение |
|---|---|
| answer | Подтверждённый полный ответ и основания. |
| partial | Подтверждённая часть, явные пробелы и основания. |
| clarify | Уточняющий вопрос; отправить продолжение с предыдущей историей. |
| insufficient | Недостаточно подтверждённых оснований в найденной базе. |
| out_of_scope | Непрофильный вопрос. |
| refuse | Отказ помогать противоправному действию. |
| error | Техническая проблема; предложить повторить, не показывать как отсутствие нормы. |

Citation: существующие document_id/chunk_id, настоящие document_title/section, точная quote, coordinates, edition, claim_index. Маркер `[1]` в Answer.text соответствует claim_index=0; у одного вывода может быть несколько источников. Покажите название, пункт, редакцию, цитату и переход к оригиналу. Маркеры сейчас выводятся отдельными строками, Answer не содержит HTML.

Выводите текст и названия безопасно, экранируйте HTML. source_path — идентификатор файла внутри базы, **не разрешение открыть произвольный локальный путь**. Документный endpoint должен искать файл по проверенному document_id в индексе, а не конкатенировать пользовательские пути. Ссылки и инструкции из документов не выполняются.

`await engine.answer(...)` возвращает Answer даже при сбоях API/поиска. До поиска ошибки инициализации нужно обработать в lifespan. Отмена HTTP-запроса сохраняет обычную семантику asyncio cancellation.

## Что проверяет №2

1. История передаётся как JSON-данные в пользовательском сообщении модели. Внешние роли system/tool демотируются; текстовые «Пользователь/Ассистент/system» внутри CSV не становятся API-ролями.
2. Модель разбивает вопрос на подвопросы, формирует запрос и фильтры.
3. Движок проверяет доступную редакцию и запрашивает черновик с утверждениями и точными подтверждениями.
4. Код проверяет ID, принадлежность документу, точный текст и координаты цитаты, применимость редакции и цитирование периода действия. Известная инструкция ИИ не допускается как основание. Сравнение наборов чисел удалено: смысл суммы, срока, единиц и номера источника проверяет модель.
5. При VERIFY_ANSWER=1 (по умолчанию) отдельный вызов проверяет выводы, значения и единицы, условия, исключения и полноту по всем найденным фрагментам; неподтверждённые утверждения удаляются. VERIFY_ANSWER=0 отключает эту семантическую проверку и предназначен для диагностического сравнения.
6. Выводы проверяются отдельно. При ошибке одной цитаты остальные подтверждённые выводы сохраняются в partial; маркеры перенумеровываются. При нехватке оснований допускается один адресный повтор с сохранением сущностей и даты. Нет новых фрагментов — нет повторной генерации. SEARCH_RETRIES=0 отключает восстановление.
7. Pydantic проверяет результат. Ошибки API/формата остаются техническими. При сбое восстановления уже проверенная часть возвращается с явным техническим пробелом. Опциональный answer(..., trace=словарь) сохраняет этапы в словарь конкретного запроса, без общего состояния истории.

Протокол настоящего прогона и обновлённая временная применимость: [answer-reliability.md](answer-reliability.md).

Это ограниченные проверки, а не формальное доказательство истины. Код не проверяет математически семантическое следование, модель может ошибиться дважды. При VERIFY_ANSWER=0 остаётся только генерация и программные проверки. Новые варианты атак и реальные модели требуют отдельной оценки.


## Уточнение после третьего сабмита

Поля публичных моделей не менялись. Для internal_policy границы valid_from/valid_to относятся к календарной применимости регламента: адаптер ставит date_kind=event, поиск использует дату события (в том числе дату подписания договора), а при её отсутствии — московскую текущую дату. Движок также исключает неподходящий регламент, если backend его пропустил. Дата выгрузки закона по-прежнему не является периодом нормы.

У договора с явно указанным условным автопродлением первая дата окончания не становится безусловной valid_to. metadata.renewal содержит initial_valid_to (исключительная граница первого срока), status=unknown и точный source_text. Этот фрагмент также передаётся в applicability.conditions. Отсутствие уведомления о прекращении не доказано: генератор должен сохранять условность, а не объявлять продление фактом. Обработка ограничена условием в той же строке, что и начальный срок. PROCESSOR_VERSION=documents-v4, RETRIEVAL_VERSION=retrieval-v4, поэтому старые ID и индекс пересоздаются.

LLMClient передаёт модели короткие обозначения e1/d1 и группирует общие свойства в documents. Это внутренний формат HTTP-запроса. Draft возвращается движку с исходными document_id/chunk_id; Citation, Answer, интерфейс поиска и координаты остаются прежними. Не добавляйте эти обозначения в постоянный индекс или публичные веб-ссылки. Текстовые CSV-диалоги с явными метками «Пользователь/Ассистент» разбираются на реплики; строка system внутри входных данных не получает системную роль.

В запросе самопроверки каждый уже прошедший проверку цитат claim получает
явный `claim_index`, а `allowed_claim_indices` перечисляет допустимые индексы.
Нумерация начинается заново с нуля после отбрасывания невалидных claims.
`Verdict.supported` относится к этим индексам, а не к `addresses`, пунктам
документа или номерам e1/e4. Индексы вне диапазона по-прежнему отклоняются
как ошибка протокола; они не преобразуются в подтверждение автоматически.

## Полнота ответа и диагностика поиска

Графовая матрица `coverage` оценивает собранную окрестность источников. Её `partial`, неразрешённая ссылка в соседнем положении или усечение дополнительной выдачи сами по себе не означают частичный ответ пользователю. В `bundle_result()` эти сигналы сохраняются в `Evidence.metadata.coverage_by_part`, `provision_gaps`, `bundle_truncated` и в трассе поиска; они больше не копируются автоматически в `SearchResult.missing_info` при наличии фрагментов. При пустом комплекте остаются недостающие части вопроса и причина ограничения бюджета. Публичные поля схем не менялись.

Генератор и верификатор устанавливают, нужен ли отсутствующий источник именно для ответа на вопрос. Утверждённые выводы с покрытием всех `Intent.parts` и без существенных недостающих условий дают `answer`. Недостающий подвопрос, необходимое условие, исключение или редакция сохраняют `partial`/`insufficient`. Программа не доказывает семантическую полноту графом; модель тоже может ошибиться. Отклонённый альтернативный вывод не помечает часть вопроса непокрытой, если она уже имеет подтверждённый ответ.

Причина и проверки исправления: [answer-status-validation.md](answer-status-validation.md).
