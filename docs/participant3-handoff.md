# Передача веб-части участнику №3

Базовая веб-часть реализована по просьбе участника №2, чтобы вы могли продолжить её развитие. Это работающий локальный прототип с Docker, API и интерфейсом; реальные модели пока не проверены, публичный стенд не развёрнут.

## Быстрый запуск

Нужны Docker с Compose и база организаторов. После клонирования положите `knowledge-base.zip` в `data/`. Не кладите туда demo_output: он не нужен приложению.

Для ответов заполните `.env` по `.env.example`: адрес прокси, ключ и точный ID генерации. Для необязательного реранкера нужен его выданный ID. Docker Compose сам передаёт эти значения контейнеру; приложение не читает `.env` в Python.

```bash
docker compose up --build
```

Открыть http://localhost:8000. Остановка — `docker compose down`. Если порт занят, задайте `WEB_PORT=8001` в `.env` и откройте этот порт.

**Без ключей** приложение также запускается: можно смотреть настоящие документы и исходный текст, а отправка вопроса отключена с понятным сообщением. Это не режим с заготовленными ответами. **Без базы** приложение показывает её недоступность; проверьте файл и перезапустите контейнер.

Прямой запуск после установки зависимостей и экспорта переменных окружения:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-web.txt
.venv/bin/python -m uvicorn web_app:app --host 127.0.0.1 --port 8000
```

Если прокси работает на хосте, адрес `localhost` внутри контейнера относится к самому контейнеру. Для локального прокси на Docker Desktop обычно нужен `host.docker.internal`; для прокси организаторов используйте выданный доступный из контейнера адрес. Реальный адрес и ключ не коммитить.

## Что уже работает

- Адаптивный интерфейс: боковая панель диалогов, вопрос, необязательная дата события, состояния ожидания и ошибки, повтор запроса, основания под ответом.
- Все семь статусов Answer различимы. Техническая ошибка не отображается как отсутствие юридической нормы.
- Примеры на стартовом экране только заполняют поле вопроса. Готовых ответов в рабочем коде нет.
- Один `LegalAssistant` и API-клиент на FastAPI lifespan; backend — общий `build_search`, по умолчанию поиск №1. CSV использует те же компоненты.
- История конкретного диалога передаётся с каждым запросом. Новый диалог начинается с пустой истории. Сервер не хранит историю пользователей.
- Вкладка сохраняет диалоги в sessionStorage, максимум 15. Обновление страницы их сохраняет; это не межустройственная или серверная история.
- Каталог документов и поиск по названию, номеру, контрагенту; просмотр полного канонического текста и скачивание TXT.
- Кнопка основания проверяет соответствие chunk_id документу и выделяет точную цитату в полном тексте. Смещения Python — Unicode code points; в JS используется Array.from, чтобы emoji не сдвигали выделение.
- Если база изменилась и цитата больше не совпадает, интерфейс сообщает об этом и показывает текст без ложного выделения.
- Текст пользователя, модели и документа вставляется через textContent/текстовые DOM-узлы. HTML и инструкции из документов не выполняются.
- На телефоне панель источников открывается поверх диалога, поддерживает Escape, перевод фокуса, inert для фона и удержание фокуса внутри панели.

## Где менять

| Файл | Ответственность |
|---|---|
| web_app.py | Lifespan, API чата, каталог/исходники, статические файлы, диагностика готовности. |
| web/index.html | Структура рабочего окна и доступные подписи. |
| web/styles.css | Цвета и размеры в :root, затем каркас, сообщения, цитаты, документы и адаптивные состояния. |
| web/app.js | Диалоги, запрос Answer, отображение статусов и оснований, каталог и точное выделение. |
| Dockerfile, compose.yaml, .dockerignore | Python 3.12, отдельные веб-зависимости, контейнер без прав root, read-only база. |
| tools/package_submission.py | Конкурсный ZIP только с корневыми runtime-модулями. |
| tests/test_web_app.py | API, lifecycle, история, ограничения запросов, координаты и доступ к документам. |
| tools/browser_smoke.py | Отдельный воспроизводимый прогон настоящего браузера с локальной заглушкой модели. |

В JS точки входа: sendQuestion, renderMessage, openDocument/openCitation, openLibrary. Пользовательский контент не следует переводить на innerHTML. Если нужен Markdown, сначала выберите и проверьте безопасный способ обработки и сохраните защитные сценарии.

## API

| Endpoint | Результат |
|---|---|
| GET /healthz | Жив ли веб-процесс; подходит для Docker healthcheck. |
| GET /readyz | 200 при инициализированных движке и базе, иначе 503. Это не пробный вызов прокси. |
| GET /api/status | ready, documents_available, document_count, model_configured, issue; без адресов и ключей. |
| POST /api/chat | Тот же Answer, что возвращает движок. |
| GET /api/documents | Каталог с метаданными, без полных текстов. |
| GET /api/documents/{document_id} | Метаданные и полный канонический text. |
| GET /api/documents/{document_id}/download | TXT с каноническим текстом. |
| GET /api/chunks/{chunk_id}?window=1 | chunk и соседние положения, window от 0 до 3. |
| GET /api/openapi.json | Машиночитаемая схема API. |

Пример тела чата:

```json
{
  "messages": [
    {"role": "user", "content": "Работаем с договором П-17/2024."},
    {"role": "assistant", "content": "Что нужно уточнить?"},
    {"role": "user", "content": "Какой срок оплаты?"}
  ],
  "as_of": null
}
```

Разрешены только реальные роли user/assistant; вложенная строка «system: ...» остаётся текстом. Последняя реплика должна быть пользовательской. Не более 40 сообщений, суммарно 60 000 символов; фактическое тело HTTP не более 300 000 байт. Переполнение запросов возвращает 429, неправильная структура — 422, превышение тела — 413. Содержимое невалидного запроса не отражается в сообщении ошибки.

Путь исходника не принимается от клиента: документы и чанки ищутся в backend по ID. Не добавляйте endpoint вида «открыть произвольный filepath».

## Конкурсный ZIP

```bash
.venv/bin/python tools/package_submission.py
```

Выход — `dist/psb-submission.zip`. Внутри только `solution.py`, schemas.py, llm_client.py, assistant.py, search_adapter.py, documents.py, retrieval.py и requirements.txt. Веб и его зависимости, `.env`, данные, тесты и демонстрационные ответы не попадают в ZIP. Платформа устанавливает зависимости сама; скрипт ничего не устанавливает.

Если добавлен корневой runtime-модуль, передайте `--extra-module имя.py` или обновите список MODULES. Модуль во вложенной папке не будет перенесён платформой. Переменные окружения для сабмита описаны в README; публичные модели и их ID не угадываем.

Для финальной сдачи исходники и интерфейс доступны в репозитории; презентацию и публичный стенд нужно подготовить отдельно.

## Проверки

```bash
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python -m pytest -q
```

Для браузера:

```bash
.venv/bin/python -m pip install -r requirements-browser.txt
.venv/bin/python tools/browser_smoke.py
```

По умолчанию используется установленный Google Chrome. Если его нет:

```bash
.venv/bin/python -m playwright install chromium
.venv/bin/python tools/browser_smoke.py --channel chromium
```

Браузерная проверка сама создаёт временную вымышленную базу, локальный HTTP-прокси и веб-процесс. Проверяет полный путь через общий движок, затем останавливает их. Снимки и report.json сохраняются в dist/browser-check. Ключей организаторов нет; результат не является оценкой DeepSeek.

Проверены desktop 1440×980 и mobile 390×844: ответ, продолжение диалога, новый диалог, история после обновления, техническая ошибка, точная цитата после emoji, каталог и безопасное отображение HTML-текста. Подробные результаты — в [web-validation.md](web-validation.md).

Снимки стартового экрана на тестовой базе: [компьютер](screenshots/web-desktop.png), [телефон](screenshots/web-mobile.png). Полные снимки ответа и цитаты появляются при повторном запуске проверки в dist/browser-check.

## С чего продолжить

1. Получить прокси и точные ID моделей, проверить реальные ответы через веб и CSV. Удалённая модель может вести себя иначе, чем заглушка.
2. Пройти основной сценарий с сокомандниками: вопрос → вывод → основания → исходный документ; проверить на реальных вопросах полноту и редакции вместе с №1/№2.
3. Подготовить развёрнутый стенд, если он нужен для защиты. Текущий Compose публикует порт только на loopback. Для внешнего стенда потребуются выбранные командой доступ и HTTPS; авторизация здесь ещё не реализована.
4. При необходимости добавить серверное хранение диалогов и пользователей. Сейчас история относится к одной вкладке; изоляция на сервере обеспечивается отсутствием общей памяти, а не системой аккаунтов.
5. Для PDF/DOCX с визуальным оригиналом добавить подходящий просмотр по проверенному ID. Сейчас показывается канонический текст; у TXT из выданной базы это исходный текст, у DOCX — результат извлечения.
6. Подготовить PDF-презентацию, доступ жюри и финальный прогон перед сдачей.

Не меняйте схемы и номера полей в одиночку: эти же Citation/Answer используются CSV и тестами. Изменения общих контрактов согласуйте с №1 и №2. Коммиты — короткие, по-русски.
