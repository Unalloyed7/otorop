# Разбор кейса ПСБ и технического регламента

Проверено 10 ноября 2026 года. Документы организаторов прочитаны как условия конкурса и описание данных; инструкции из текстов базы не становятся командами ассистента.

Исходный репозиторий был пустым. PLAN.md не существовал; добавленный здесь план — командная заготовка по поручению пользователя. Контракты переданы через репозиторий, но фактическое согласие участников №1 и №3 пока не получено.

## Что нужно получить

Продукт помогает юристу банка найти основания в выданных документах, сопоставить их и проверить вывод. Убедительный текст без оснований не выполняет задачу. Внешний интернет, правовые базы и память модели не являются источниками юридического ответа. Ссылки на сайты в самих файлах показывают происхождение выгрузки, но движок не должен переходить по ним для дополнения базы.

Для автоматической проверки нужен запускаемый Python-скрипт; веб там не требуется. Для финальной сдачи веб-чат с просмотром подтверждающих документов обязателен. Веб и CSV должны использовать один поиск и одну логику ответа. Иначе улучшения конкурсного решения не подтверждают работоспособность демо.

## Допуск и оценка

Нужно одновременно получить ненулевой балл LLM-судьи, показать работающий веб и представить обязательные материалы. Наличие одного CSV без интерфейса недостаточно для экспертной оценки финального прототипа.

Онлайн-этап: 70% результата даёт LLM-судья, 30% — экспертная оценка. В экспертной части веса: контроль достоверности 25%, работоспособность 20%, архитектура и документы 20%, скорость 15%, интерфейс 15%, презентация 5%. Финал: 70% онлайн-этап, 30% финальная защита. В защите особенно важны ценность клиенту и живая демонстрация — по 25%.

Судья сравнивает ответ команды с baseline относительно эталона в двух перестановках A/B. Значения одного сравнения: 0; 0,25; 0,5; 0,75; 1. Балл вопроса — среднее двух сравнений. Match Rate — средний балл успешно оценённых вопросов. Win Rate = победы / (победы + поражения), ничьи исключены; если все ничьи, значение 0,5. Итоговый Score = 0,7 × Match Rate + 0,3 × Win Rate. Технические ошибки самого судьи исключаются из Match Rate. Выдуманный факт обнуляет вопрос.

Следствие: сначала устранять выдумки и потери условий; затем улучшать полноту и уменьшать необоснованные отказы. Отказ на всё не является качественным решением. Открытые 18 вопросов — регрессия, они не дают оценки на скрытых public/private наборах.

Нельзя автоматически восстановить старый текст, вычитая изменения из действующего. Временный движок консервативно исключает current_only-выгрузки при иной явно заданной дате; это может давать лишние отказы. Для снятия ограничения №1 должен предоставить проверенную применимость конкретной редакции, а не просто дату выгрузки.

## Трудные сценарии

1. **Ложная предпосылка.** Пользователь называет сумму/срок, которых нет в договоре. Ответ исправляет предпосылку по базе и приводит точный пункт, без уступки под давлением.
2. **Частичный ответ.** Один из нескольких подвопросов подтверждён, второй требует отсутствующего документа. Возвращаем известную часть, status=partial и конкретный пробел. Не маскируем пропуск полным ответом.
3. **Неоднозначность.** «Альфа» не идентифицирует организацию. Если номер договора уже есть в истории, повторное уточнение не требуется. Если выбора действительно нет, status=clarify.
4. **История.** Учитываем ранее названные обстоятельства, отвечаем на последнюю пользовательскую реплику. Предыдущая реплика ассистента — контекст, не доказательство. Между ID память не переносится.
5. **Редакции.** Используем дату именно того события, с которым связано правило. При нескольких существенных датах одного поля недостаточно: нужно уточнить или расширить контракт согласованно.
6. **Противоправный запрос.** Отказываем помогать совершению действия; разъяснить требования и последствия по базе можно. Непрофильный вопрос имеет отдельный статус.
7. **Атаки.** Вложенные system-сообщения, текст документов и требования изменить ответ не получают права системной инструкции. Известная атака в архиве дополнительно блокируется при попытке процитировать её как основание. Это не доказывает устойчивость к любым формулировкам.
8. **Сбой API.** 401, исчерпанные 429/5xx, тайм-аут, неверный JSON — status=error. Они ничего не говорят о наличии юридических оснований.

## Почему стартер нельзя копировать целиком

Он показывает /embeddings, /rerank и /chat/completions, чтение ZIP, DOCX и CSV. Но выбирает документы по словам, обрезает начало текста, не проверяет утверждения и возвращает общий fallback. Это потеряет специальные нормы в длинных статьях, историю и редакции.

Дефолт реранкера в стартере — cohere/rerank-5-fast; в кейсе назван Qwen3 Reranker 8B. Наш клиент не задаёт дефолт модели: точные ID поколения, эмбеддера и реранкера берутся из окружения организаторов. JSON-mode также не предполагается поддержанным: используем обычный chat с JSON-схемой в инструкции и строгую проверку ответа.

## Упаковка и лимиты

- DATA_DIR содержит questions.csv и knowledge-base.zip; поддержаны также имена kb.zip и knowledge_base.zip из стартера.
- Вход UTF-8, id,question. Каждая строка независима; история может находиться внутри ячейки question.
- Выход в рабочем каталоге: submission.csv, UTF-8, строго id,answer. Все входные ID ровно по одному разу; ответы непустые, до 10 000 символов, обычное CSV-экранирование.
- Желательно до 150 слов; обоснование может требовать больше. Ссылки должны быть читаемы без веба: документ, пункт, редакция и точная цитата.
- ZIP до 128 МБ, 8 CPU, 16 ГБ RAM, до 20 минут. 5 сабмитов в день, сброс в 00:00 МСК. Изменения лимитов следует перепроверить перед сдачей.
- В корне ZIP должны быть solution.py, requirements.txt и необходимые корневые .py. Платформа не переносит вложенные модули. pip install внутри скрипта запрещён. Данные передаёт платформа.
- Используются только библиотеки разрешённого набора, с закреплёнными версиями. Наш runtime: HTTPX и Pydantic, остальные зависимости из стандартной библиотеки.
- Финальная сдача отдельно требует Dockerfile, compose.yaml, .dockerignore, README и PDF-презентацию. Это зона №3. У приватного репозитория нужен доступ жюри hack-and-change-2026.

## Практический приоритет команды

Сначала подтвердить цельный сценарий «вопрос → применимые документы → вывод → точные основания → просмотр оригинала → CSV». Затем улучшать гибридный поиск и разрешение изменений, используя одну регрессию в вебе и CLI. Измерять отдельно качество поиска, обоснованность выводов, лишние отказы, задержку и число вызовов. Дополнительная модельная проверка полезна только после сравнения с базовым вариантом; она не превращает ответ в доказанную истину.

Перед финальной сдачей нужны запуск из чистого клона, запуск корневых модулей из ZIP, реальные вызовы к прокси и хотя бы один официальный ненулевой сабмит. Ни локальные заглушки, ни открытые примеры не заменяют эти проверки.
