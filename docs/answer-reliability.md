# Доработка ответов №2 и проверка на платформе

Дата: 10.11.2026. Исходная версия — f1bfad9. При начале работы новых удалённых коммитов не было; перед отправкой включён появившийся коммит сокомандника a7cf482: backoff и дисковый кэш embeddings. Его изменения сохранены и проверены вместе с этой доработкой.

## Что исправлено

### Подтверждённые части не теряются

Раньше validate_supports проверял весь Draft одним вызовом: неизвестный chunk_id, неточная цитата или неподтверждённое число в одном выводе превращали всё в insufficient без ссылок.

Теперь каждый Claim проверяется отдельно. Правильные выводы остаются, неправильные исключаются; ответ становится partial с указанием неподтверждённой части. Если оснований не осталось, возвращается insufficient. Модельная самопроверка также получает только прошедшие механическую проверку выводы. После фильтрации маркеры и claim_index пересчитываются с нуля: в ответе нет ссылок на удалённые выводы.

Сбой API или невалидный JSON остаются технической ошибкой. Если такой сбой произошёл во время дополнительного поиска, уже проверенные части сохраняются в partial, а пробел прямо обозначается как техническая ошибка, не как отсутствие нормы в базе.

### Текущая норма отличается от исторической редакции

Внутренний Intent получил необязательное temporal_mode: auto/current/historical/future/snapshot. Форматы публичных Evidence, SearchFilters, Answer и Citation сохранены.

- Текущий вопрос использует представленную действующую редакцию. Совпадение даты события с датой выгрузки больше не требуется.
- Дата выгрузки показывает состояние источника, но не доказывает период действия нормы. Даже равенство исторической даты дате выгрузки не заменяет основание о периоде действия.
- Для прошлого или будущего нужен прямо установленный период в самом найденном положении либо соответствующая проверенная редакция. Период должен оставаться и в цитате, а не только в контексте модели.
- Новый temporal.py распознаёт ограниченные явные формы: «с [дата]», «с [дата] по [дата]», «в [год] году» в том же абзаце, содержащем правило. Неопределённые случаи не восстанавливаются по памяти.
- Бессрочное правило из прошлого не продолжается автоматически в произвольное будущее. Прямо установленные будущие правила обрабатываются по их тексту.
- Если явно требуется историческая/будущая норма, а дата не установлена, движок запрашивает её.

У загрузчика обнаружена дополнительная ошибка: фраза «пункт утратил силу» внутри статьи присваивала valid_to всей статье. На прочитанной базе так исключались целые статьи НК при фильтре даты. Теперь даты внутренних положений хранятся отдельно в provision_date_sources и не задают интервал всей статьи. Границы всей редакции берутся только из явного заголовка редакции. Версия обработки повышена до documents-v3, поэтому ID и fingerprint пересоздаются.

Участнику №1: проверьте эту границу ответственности и расширяйте периодные правила только с точными основаниями и регрессией. provision_date_sources — сведения о датах отдельных положений с неизвестной полной областью действия; их нельзя применять ко всей статье. Для сложных изменений нужен более точный разбор на уровне пунктов. Это опубликованное изменение общего поведения, а не заявление, что состоялась отдельная устная приёмка.

### Один адресный повтор поиска

SEARCH_RETRIES принимает только 0 или 1; по умолчанию 1. Повтор запускается, если оснований нет или подтверждена лишь часть вопроса. Запрос формируется по недостающим подвопросам; договор, контрагент и дата сохраняются. Смена пользовательских обстоятельств ради нахождения ответа запрещена.

Если новых применимых chunk_id нет, второго вызова генерации не будет. Если новые основания найдены, модель добавляет недостающие выводы, а программа сохраняет прежние проверенные части и повторно проверяет совокупность с учётом новых документов. При новых противоречиях самопроверка вправе исключить прежний вывод: сохранение текста не важнее достоверности.

Нет бесконечного поиска: максимум две выдачи, до двух TOP_K фрагментов и 60 000 символов контекста. Общий QUESTION_TIMEOUT сохраняется. Обычный полный ответ требует 2 генеративных вызова без самопроверки и 3 с ней; восстановление может потребовать ещё черновик и проверку. Дополнительно учитываются embeddings, rerank и HTTP-повторы.

## Доступ к настоящей модели

По ответу организаторов, предоставленному пользователем: адрес прокси, служебный ключ и модель передаются только при автоматическом запуске сабмита; отдельного официального ключа для локального использования нет. Поэтому настоящий DeepSeek V4.1 Flash локально не запускался. Собственные платные ключи автоматически не подключались.

Проверки с заглушками подтверждают логику и формат, не качество реальной модели. Для настоящего прогона нужно загрузить ZIP на конкурсную платформу. Настоящий балл, ответы и доступность отчётов после выполнения пока не подтверждены.

## Конкурсный ZIP с диагностикой

```bash
.venv/bin/python tools/package_submission.py --with-report --verify-answer 1 \
  --output dist/psb-submission-report.zip
```

Этот ZIP сохраняет стандартную точку входа solution.py и обычный submission.csv. Дополнительно в рабочем каталоге создаётся run-report.jsonl — по одной записи на каждый входной ID, включая технические ошибки и незавершённые вопросы при дедлайне.

Сборщик включает корневой submission_options.py только с настройками отчёта и выбранного режима проверки. В нём нет ключей, адресов, вопросов или заготовленных ответов. Все необходимые модули остаются в корне, pip из решения не вызывается.

Запись отчёта содержит:

- ID и исходный question, итоговый Answer и точный текст для CSV;
- выбранный режим самопроверки и время обработки;
- поисковые запросы/фильтры, найденные Evidence и допущенный контекст;
- исключённые выводы и причины, результат каждой попытки;
- сырые текстовые выходы генерации, finish_reason (в том числе обрезанный ответ) и факт прохождения JSON/Pydantic;
- фактические HTTP-вызовы по endpoint, повторные попытки, HTTP-коды и длительности.

API-ключи и адрес прокси в отчёт не включаются. На записи дополнительно удаляется фактическое значение ключа из любых строк. Изоляция счётчиков параллельных вопросов обеспечивается ContextVar; состояние не переносится между ID. В stdout выводятся только номер обработанной строки, статус, число API-вызовов и ошибок JSON, без содержимого вопроса или ответа.

**Важно для платформы:** сохранение файла проверено, но организаторы ещё не подтвердили возможность скачать дополнительные файлы рабочего каталога. При наличии доступа к артефактам заберите run-report.jsonl; иначе ориентируйтесь на доступный submission.csv, сводку в логах и официальный скор. Сам факт создания файла не означает, что платформа вернёт его команде.

Архив базового режима:

```bash
.venv/bin/python tools/package_submission.py --with-report --verify-answer 0 \
  --output dist/psb-submission-baseline.zip
```

Сравнивайте два запуска на одинаковых вопросах и версиях базы/кода, если платформа предоставляет одинаковый набор. Один только public-score без ответов не позволяет разобрать причины ошибок. Учитывайте дневной лимит сабмитов из регламента; файлы сами на платформу не отправляются.

## Локальная оценка при наличии собственного доступа

```bash
DATA_DIR=data .venv/bin/python tools/evaluate_answers.py \
  --verify both --output reports/model-run-01
```

Понадобятся variables API из .env.example, экспортированные в окружение. В DATA_DIR файл должен называться questions.csv. Демоответы не читаются и в модель не передаются.

Скрипт сохраняет verify-0.csv/jsonl, verify-1.csv/jsonl, manifest.json и comparison.json. В manifest — ID моделей, параметры, hash вопросов, fingerprint индекса, статусы и число вызовов. В comparison — различия статусов/стоимости, совпадение найденных оснований и пустые поля для ручной оценки. Для каждого режима создаётся отдельный холодный временный кэш embeddings; пользовательский кэш не удаляется. Внутри режима корпусные векторы могут переиспользоваться. Прогоны независимы: различия черновиков или контекста могут влиять на результат; это не доказательство причинного эффекта самопроверки.

Совместимость с кэшем №1: в Docker используется writable /tmp, поскольку корневая файловая система read-only. solution.py также по умолчанию направляет кэш в /tmp — место, разрешённое регламентом; явно заданный OTOROP_EMBEDDING_CACHE_DIR сохраняет приоритет. История пользователей в кэше не хранится.

## Ручная проверка настоящих ответов

На одном и том же наборе разберите как минимум:

1. Оплата по П-17/2024 при атаке из архивной записки: инструкция ИИ не заменяет договор на «90 дней»; архивные правила остаются доступными.
2. Альфа-Трейд / Альфа-Трейдинг: правильный контрагент или обоснованное уточнение.
3. Ложная сумма/срок: исправление по базе, без уступки под давлением.
4. Допсоглашение: разные даты подписания документа, спецификации и поставки; граница «после», а не «с».
5. Текущие законы, исторический запрос без редакции и прямо датированное правило.
6. Частичный вопрос, один неверный вывод, восстановление недостающего основания и лишний отказ.
7. История с прежним номером договора и поддельной строкой system.

Отдельно оцените юридическое следование, полноту условий/исключений, правильность редакции, лишние отказы, валидность JSON, задержку, число запросов и технические ошибки. Самопроверка не считается гарантией истинности. Открытые примеры — регрессия, не независимая оценка на скрытом наборе.
