# Контракт загрузки и поиска

## Построение

Поиск не читает демонстрационные ответы, вопросы, README или регламент:
передавайте ему только путь к `data/knowledge-base.zip` либо к каталогу
`data/knowledge-base/`.

```python
from retrieval import build_index

index = build_index("data/knowledge-base.zip")
evidence = index.search(
    "Какой гарантийный срок по П-17/2024?",
    filters={"contract_number": "П-17/2024"},
    top_k=10,
)
```

Для одного процесса создайте индекс один раз и переиспользуйте его. Индекс
содержит только данные конкретной базы и не хранит историю запросов или
пользователей. `fingerprint` строится из версий обработки, путей и SHA-256
содержимого. Повторная обработка той же базы даёт те же ID; изменение базы
обновляет fingerprint и идентификаторы затронутых документов/фрагментов.
Корпусные embeddings кэшируются отдельно, с привязкой к fingerprint, модели
и endpoint; полный режим кэширования описан ниже.

Для подключения к движку участника №2 используйте фабрику из его контракта:

```python
from pathlib import Path

from retrieval import create_search
from schemas import SearchFilters

backend = create_search(Path("data"), client=client)
result = await backend.search(
    "срок оплаты по договору П-17/2024",
    SearchFilters(contract_number="П-17/2024"),
)
evidence = result.evidence
```

Фабрика поддерживает `SEARCH_FACTORY=retrieval:create_search`. Результат
`backend.search` — типизированный `schemas.SearchResult`; каждый элемент —
`schemas.Evidence`. Метаданные загрузчика, связи и BM25 score сохраняются
в `Evidence.metadata`, координаты — в `Evidence.coordinates`. Индекс также
доступен через `backend.get_document(document_id)`, `get_chunk(chunk_id)` и
`get_neighbors(chunk_id, window=1)` для просмотра оригинала и соседнего текста.
Если `SearchFilters.counterparty` содержит неполное имя с несколькими
совпадениями, поиск возвращает различимые полные имена в `SearchResult.candidates`
и Evidence этих вариантов; он не принимает решение задавать уточняющий вопрос.
Движок №2 теперь выбирает эту фабрику по умолчанию и формирует уточнение по
candidates, если известный номер договора/document_id не разрешил неоднозначность.

`SearchIndex.search`. При передаче в общий движок поля адаптируются к схеме
`schemas.Evidence` (название — `document_title`, координаты — объект
`coordinates`, дополнительные поля — `metadata`).
Пример иллюстрирует форму записи; ID и координаты конкретного корпуса нужно
получать из построенного индекса, а не копировать из документации.


Пример получен реальным запросом
`index.search("срок оплаты по договору П-17/2024", {"contract_number": "П-17/2024"}, 10)`;
координаты проверены срезом исходного текста.

`score` — относительный рейтинг BM25 с ограниченными бонусами совпадений,
поисковых синонимов и контекстных соседних пунктов; это не вероятность
истинности. Неизвестные даты/сущности имеют значение `null`.
`valid_to` — исключительная верхняя граница действия: для текста «утратил силу
с указанной даты» используется эта дата, а для «действует до» — следующий
календарный день. `edition` и `approval_date` не подменяют дату действия.
Текст всех цитат проверяется как
`document["text"][start_char:end_char] == evidence["text"]`.

Для загрузки полного текста/фрагмента используйте
`index.get_document(document_id)` и `index.get_chunk(chunk_id)`. Для соседнего
контекста вызовите `index.get_neighbors(chunk_id, window=1)`; список включает
сам фрагмент и до одного соседа с каждой стороны.

## Фильтры и даты

Низкоуровневый `SearchIndex.search` принимает фильтры `contract_number`,
точный `counterparty`, `document_type`, `document_id`, `as_of` (синонимы:
`valid_on`, `event_date`), `signed_at`, `snapshot_date`,
`specification_signed_at` и `only_applicable`. При поиске с номером договора
договоры/допсоглашения сохраняются в выборке, а общие регламенты и законы
добавляются при достаточной лексической релевантности; явно указанный закон
или статья не отсекаются этим порогом. Несвязанные похожие договоры и
контрагенты не объединяются.

Адаптер `create_search` принимает общий `schemas.SearchFilters`. `event_date`
применяется только согласно `date_kind`:

- `event`, `delivery`, `document_validity` — дата события/действия документа;
- `specification_signed` — только условие допсоглашения для даты спецификации;
- `contract_signed`, `document_signed` — сравнение с датой подписания;
- `law_snapshot` — дата выгрузки/снимка закона, не период действия нормы.

Неизвестный тип даты вызывает явную ошибку, а не трактуется как дата действия.
Источники и основание дат сохраняются в `Evidence.metadata.date_sources`;
извлечённые условия и неопределённости также передаются генератору.

```python
old_policy = index.search(
    "срок согласования договора",
    filters={"document_type": "internal_policy", "as_of": "2024-08-01"},
)
address = index.search(
    "адрес доставки П-17/2024",
    filters={"contract_number": "П-17/2024", "specification_signed_at": "2024-10-02"},
)
```

Редакции не удаляются: без фильтра даты подходящими могут быть несколько
редакций. Если историческая граница в тексте не указана, это отмечается в
`uncertainties`, а не выводится из предположений. Фильтр даты не создаёт
отсутствующую редакцию закона.
В Evidence сохраняются отдельно даты подписания, утверждения, вступления
в силу, начала/окончания действия и снимка закона, вместе с исходным текстом,
из которого каждая дата извлечена. Текущий снимок закона получает
`applicability.current_only=True`; дата выгрузки сама по себе не доказывает
период действия и не заменяет историческую редакцию.

Даты утраты силы внутренних пунктов не задают valid_to всей статьи и
сохраняются отдельно в provision_date_sources. Границы
всей редакции берутся из явного заголовка редакции. Движок различает текущий
вопрос и запрос исторической нормы; ограниченный разбор прямо датированных
положений находится в temporal.py. Для исторического/будущего вывода текст
периода должен также цитироваться. Детали и задачи для совместной проверки
№1/№2 — в docs/answer-reliability.md.

Для дополнительного соглашения № 1 к П-17/2024 условие сформулировано строго:
новый адрес применяется к спецификациям, подписанным **после** 1 октября 2024 г.
Поэтому `2024-10-01` не удовлетворяет условию, `2024-10-02` удовлетворяет.
Проверить его можно через `evaluate_applicability(evidence, date)`.
По умолчанию поиск возвращает и условный фрагмент, снабжая его статусом
`applicable`, `not_applicable` или `unknown`; `only_applicable=True` исключает
явно неприменимые фрагменты.
Адаптер передаёт этот статус в `Evidence.metadata.applicability_status`;
`applicability.resolved=True` означает лишь известность результата и может
соответствовать как applicable, так и not_applicable.

`related_document_ids` связывает документы с тем же номером договора, включая
основной договор и допсоглашение. `linked_document_ids` дополнительно содержит
явные ссылки на документы по названию и связанную редакцию регламента. Связи
доступны в обе стороны. Фильтр договора сохраняет найденные связанные
регламенты и письма, не подмешивая несвязанные законы. Это подсказки для поиска:
участник №2 должен включить соответствующие источники в контекст и оценить
условия применимости.

## Комплекты положений и граф связей

`LegalAssistant` в вебе и CSV вызывает этот API по частям вопроса; доступен
также прямой вызов без изменения общего `schemas.py`:

```python
bundle = await backend.search_bundle(
    ["кто одобряет договор", "какой пункт регламента устанавливает порог"],
    SearchFilters(contract_number="П-17/2024"),
    top_k=10,
    max_context_chars=12000,
    max_context_chunks=24,  # необязательный предел числа Evidence
    mode="hybrid",  # необязательно: bm25, semantic или hybrid
)
```

Возвращается JSON-сериализуемый словарь с полями:

- `groups` — по одной записи на часть вопроса: `part`,
  `direct_chunk_ids`, `evidence_chunk_ids`, `relation_ids`, `missing`,
  `clarification`, `candidates`, `truncated` и `omitted_chunk_ids`;
- `evidence` — полный набор фрагментов с исходными ID, текстом,
  координатами, `local_conditions`, `applicability_conditions`,
  `provision_relations`, `provision_gaps`, оценкой применимости и score;
- `relations` — рёбра между фрагментами с `from_chunk_id`, `to_chunk_id`,
  `type`, `target_reference`, `confidence`, точной `quote` и
  `supporting_chunk_ids`;
- `gaps` и `missing_parts` — неразрешённые ссылки/отсутствующие фрагменты и
  части вопроса без прямой выдачи;
- `context_spans` — объединённые неперекрывающиеся диапазоны по исходному
  документу, с точным `text` и `source_chunk_ids`;
- `context_chars` — размер объединённых исходных диапазонов;
- `evidence_chars` — сумма длин реально передаваемых Evidence, включая
  перекрытие; именно она ограничивается `max_context_chars`;
- `max_context_chars`, `max_context_chunks`, `truncated` и `omitted_chunk_ids`
  — сведения о применённом бюджете контекста.

Пример ребра:

```json
{
  "type": "changes_provision",
  "from_chunk_id": "<исходный пункт договора>",
  "to_chunk_id": "<новая редакция пункта>",
  "target_reference": "3.2",
  "confidence": "explicit",
  "quote": "Изложить пункт 3.2 договора в следующей редакции:",
  "supporting_chunk_ids": ["<фрагмент с директивой изменения>"]
}
```

Поддерживаются `changes_provision`, `supplements_provision`,
`removes_provision`, `replaces_provision`, `defines_applicability`,
`supersedes_edition`, `establishes_exception`, `supplements_procedure`,
`references_provision` и `possible_exception_to`. Последний тип имеет
`confidence="inferred"`: это эвристическая связь, а не подтверждённая текстом
ссылка. Явные отношения имеют `confidence="explicit"` и сопровождаются
фрагментом, подтверждающим связь. Отсутствующая или неоднозначная цель
сохраняется в `gaps`; факт ссылки не дополняет базу текстом отсутствующего
положения.

`search_bundle` расширяет выдачу по графу до связанных пунктов, исключений,
условий и фрагментов-подтверждений (до трёх переходов по графу). Для каждого
добавленного положения обязательно восстанавливаются все его части и
вводные положения предков, включая положения на последнем переходе графа.
Объединённые диапазоны сохраняются отдельно, не теряя происхождение.
Каждый новый комплект зависимостей добавляется целиком,
только если он помещается в пределы символов и числа фрагментов; иначе новые для результата
фрагменты помечаются в `truncated` / `omitted_chunk_ids`. Уже добавленные
общие фрагменты остаются доступными. Проверяйте срез каждого `context_spans`
по исходному тексту документа. Для отображения цепочки №3 использует
`relations` и может получить оригиналы через `backend.get_document(document_id)`
и `backend.get_chunk(chunk_id)`.

`backend.bundle_result(bundle)` возвращает `SearchResult` для движка с теми
же исходными ID и координатами. Ограничение контекста явно добавляет пробел
в `missing_info`, а трассировка сохраняет группы, связи и пропущенные ID.
При повторном поиске `existing_chunk_ids` входят в общий бюджет;
`query_context` сохраняет уточнённые сущности и контекст запроса при поиске
каждой части. Backend только с `search` остаётся совместимым.

## CLI и проверка

```sh
.venv/bin/python retrieval.py data/knowledge-base.zip \
  --query "адрес доставки П-17/2024" --top-k 10 --stats
.venv/bin/python -m pytest -q
```

`SchemaSearchBackend.search` использует hybrid (BM25 + dense cosine) при
настроенном `EMB_MODEL`, и BM25 без API — при отсутствии настройки. Корпусные
embeddings строятся пакетами и кэшируются в JSON вне репозитория в
`~/.cache/otorop/embeddings/` (либо в `OTOROP_EMBEDDING_CACHE_DIR`, если задан).
Ключ кэша учитывает fingerprint базы, модель и API base URL; запись атомарная.
Изменение базы или модели приводит к новому файлу кэша. Векторы запросов не
кэшируются между вызовами. Повреждённый или несовместимый кэш диагностируется
и перестраивается.

При ошибке embeddings текущий запрос сразу продолжает работу через BM25.
Следующие запросы временно используют BM25 без обращения к недоступной модели:
первая пауза — 30 секунд, затем задержка удваивается до максимума 5 минут.
После паузы выполняется новая попытка; при успехе hybrid восстанавливается и
счётчик ошибок сбрасывается. Сбой необязательного reranker также диагностируется
и не отменяет результаты retrieval. ID моделей читаются из конфигурации
`LLMClient`, не задаются в коде.
Явные режимы доступны через `backend.search_with_mode(query, filters, mode)`
для `bm25`, `semantic` или `hybrid` (без реранкера, чтобы сравнение было
сопоставимым).

Для сравнения режимов подготовьте CSV с вручную размеченными
`relevant_chunk_ids` (несколько ID разделяются `;`; `filters_json` необязателен).
Для текущего открытого корпуса ID пункта 2.4 действующего регламента можно
получить так:

```csv
query,relevant_chunk_ids,filters_json
"кто должен одобрить договор","<chunk-id-2.4>"
"кто одобряет договор","<chunk-id-2.4>"
```

```sh
# Сначала получите ID нужного положения из той же базы:
.venv/bin/python -c 'from retrieval import build_index; i=build_index("data/knowledge-base.zip"); print(next(c["chunk_id"] for c in i.chunks if "Регламент согласования договоров ред 2025" in c["source_file"] and c.get("section_reference") == "2.4"))'
# Подставьте этот ID в обе строки retrieval_cases.csv, затем запустите:
.venv/bin/python retrieval.py data/knowledge-base.zip \
  --compare-csv retrieval_cases.csv --top-k 10
```

Команда выдаёт recall@k по каждому запросу и средний recall@k для BM25,
semantic и hybrid на одинаковом наборе. Она запускает API только для
семантических режимов и берёт модели/ключ/адрес из переменных окружения,
переданных организаторами (`LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`,
`EMB_MODEL`). Эти значения нужно настроить в окружении запуска, не передавать
в аргументах CLI; ключ нельзя помещать в CSV, код или логи.
Без настроенного API сравнение явно помечает semantic/hybrid недоступными,
а BM25 продолжает работать.

## Воспроизводимая индексация и pipeline relations

Индекс строится только по переданному ZIP/каталогу базы знаний. Этапы
структурного разбиения, сущностей, ссылок, кандидатов отношений, проверки
цитат и графа сохраняются в локальный SQLite-кэш. По умолчанию путь находится
в `~/.cache/otorop/knowledge/`; `OTOROP_KNOWLEDGE_CACHE_DIR` задаёт каталог,
а `--pipeline-cache` — точный файл. Кэш раздельный по пути базы и содержимому:
изменённые документы проходят нужные этапы заново, неизменённые загружаются
из кэша. При изменении входного содержимого fingerprint графа меняется.
В Docker каталог кэша по умолчанию — `/tmp/otorop/knowledge`, поскольку
корневая файловая система контейнера доступна только для чтения. Compose
передаёт `OTOROP_KNOWLEDGE_CACHE_DIR` и настройки LLM-извлечения из окружения.
Стандартный tmpfs-кэш сохраняется в течение жизни контейнера; для сохранения
между пересозданиями контейнера нужен отдельный доступный для записи volume.

```sh
# Построить/обновить кэш и показать фактическое состояние стадий
.venv/bin/python retrieval.py data/knowledge-base.zip \
  --pipeline-cache .cache/knowledge.sqlite3 --stats

# Пример BM25-поиска без обязательного API
.venv/bin/python retrieval.py data/knowledge-base.zip \
  --pipeline-cache .cache/knowledge.sqlite3 \
  --query "адрес доставки по договору П-17/2024" --top-k 10

# Необязательное ограниченное извлечение связей через общий LLMClient
.venv/bin/python retrieval.py data/knowledge-base.zip \
  --pipeline-cache .cache/knowledge.sqlite3 --llm-relations
```

Для веб/CSV путь №2 не меняется: `create_search(data_dir, client)` использует
`SchemaSearchBackend`; при `KNOWLEDGE_LLM_EXTRACTION=1` каждый внешний вызов
`search` или `search_bundle` продвигает обработку на одну порцию. Части одного
`search_bundle` не увеличивают бюджет. CLI-флаг `--llm-relations` и явный
`prepare_knowledge_graph()` также выполняют по одной порции. Лимит
`KNOWLEDGE_LLM_MAX_CHUNKS` — от 1 до 64 (по умолчанию 16) новых вызовов,
загрузка успешных результатов из кэша его не расходует. Все фрагменты корпуса
входят в очередь, включая не содержащие ключевых слов и явных ссылок.
Текст документа передаётся как недоверенные данные.
Успешные результаты извлечения и обогащённый граф кэшируются отдельно по
корпусу, endpoint, модели, версии промпта и фрагментам. Успешные стадии в
SQLite образуют сохраняемую очередь: следующий вызов, в том числе после
перезапуска, берёт оставшиеся фрагменты, а не первую порцию заново. Новая
работа выполняется перед повторами ошибок; ошибочные фрагменты повторяются
в порядке последней попытки. Цитата вне источника считается ошибкой стадии.
Частичный граф восстанавливается из успешных стадий без повторного добавления
рёбер; завершённый снимок сохраняется только после обработки всей очереди.
Ошибка enrichment видна в diagnostics и не выключает BM25.

Отчёт `pipeline.llm_relations` содержит `status`, `coverage_complete`,
`total_chunks`, `completed_chunks`, `remaining_chunks`, `attempted_chunks`,
`cached_chunks`, `budget_exhausted`, `relations` и `failures`. Пока остаются
необработанные/ошибочные фрагменты, статус — `partial`. `complete`/`cached`
означает завершение извлечения для всего корпуса, а не доказанную полноту
юридических связей или корректность всех их типов.

Явно указанное название, номер договора или нормативный акт ограничивает
поиск цели этим документом. Отсутствующая цель не заменяется локальным
одноимённым пунктом. При нескольких подходящих положениях изменение остаётся
неоднозначным; прежний построитель также не создаёт рёбра изменения и условия
для такого случая. Новые версии графа/разрешения целей исключают восстановление
старых ошибочных снимков.

## Известные ограничения

- BM25 остаётся полностью офлайн-доступным. Dense и hybrid режимы используют
  подключённый `LLMClient`; reranker применяется к штатной выдаче только когда
  задан `RERANKER_MODEL`. Корпусные векторы занимают память процесса и имеют
  дисковый кэш с привязкой к fingerprint, endpoint и model ID. На этой машине нет настроек
  прокси/API, поэтому реальные bge-m3 и Qwen3 Reranker 8B вызовы и измерение
  качества моделей не выполнялись; сравнение через тестовый векторизатор
  проверяет только маршрутизацию, fallback и метрику, но не качество моделей.
- Метаданные автоматически извлекаются эвристиками из доступных текстов и
  имён файлов. Неизвестные даты/сущности остаются пустыми; `score` не является
  вероятностью истинности.
- Детерминированное извлечение графа покрывает типовые нумерованные ссылки,
  диапазоны и упоминания документов, но не является полным юридическим
  парсером. Неоднозначные/неразрешённые цели сохраняются как gaps, а не
  выбираются эвристически. LLM-enrichment выключен по умолчанию, ограничен
  выбранными фрагментами и требует настроенного общего API-клиента; даже
  успешный структурированный вывод остаётся кандидатом и не доказывает
  юридическую семантику или временную применимость связи.
- Даты и условия применимости фильтруются только когда они явно извлечены или
  переданы вызывающей стороной. Поиск не восстанавливает отсутствующие редакции
  законов, не принимает решение об отказе и не защищает генератор от инструкций
  внутри документов.
- Основной BM25-индекс строится в памяти при вызове `build_index`; промежуточные
  результаты обработки и снимок детерминированного/успешного LLM-графа хранятся
  в SQLite-кэше. Векторы embeddings кэшируются отдельно по fingerprint,
  model ID и endpoint.

Текущие версии обработки: `documents-v6`, `retrieval-v8`, версия embedding-кэша
— 2. Условия применимости сохраняются отдельными точными фрагментами с
координатами в исходном тексте и ссылкой на целевой пункт, когда она
устанавливается. Условие отдельного подпункта не переносится автоматически на
прочие положения документа.

Разбиение реализовано в `structural_chunking.py`. Единица — статья или
нумерованный пункт с продолжениями, абзацами, условиями и перечислениями
`1)`, `2)`. Физический перенос строки внутри пункта не создаёт новый фрагмент.
Дочерние пункты разделяются, но сохраняют ссылки на родительские вводные.
Ненумерованный текст группируется по абзацам, заголовки и директивы изменения
выделяются отдельно. Длинная единица делится до 1800 символов, преимущественно
на границах абзацев и предложений, затем слов; перекрытие до 180 символов
также выравнивается по границам. Неразрывный токен длиннее лимита приходится
резать по символам. Все части имеют общий `provision_id`, исходный диапазон
и список `provision_chunk_ids`. Это детерминированное структурное разбиение,
не семантическая классификация моделью; нестандартная разметка остаётся
ограничением. После смены версии ID и fingerprint меняются, старые embeddings
не используются как векторы новых фрагментов.

Проверка нового пути без API:
`.venv/bin/python tools/audit_retrieval.py --bundle --output reports/bundle.json`.
Она проверяет покрытие источников, а не юридическое качество ответа модели.

Набор `tests/test_provision_relations.py` проверяет цепочку исходный пункт →
изменение → условие по П-17/2024, точность цитат/координат, сборку комплекта,
атомарное ограничение контекста, отсутствующую ссылку и условие с переносом
строки. Сквозные проверки дополнительно проверяют передачу статуса применимости
генератору и возобновление частичного embedding-кэша.
